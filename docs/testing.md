# Пирамида тестирования «Окна»

Берём за ориентир secureshare. В локальной копии проекта есть HTTP-тесты бэкенда, Vitest и React Testing Library для фронтенда и Playwright с отдельными профилями desktop и mobile. Для «Окна» распределяем проверки по уровню, на котором можно воспроизвести сбой и увидеть его причину.

| Уровень | Что проверяем | Инструменты |
| --- | --- | --- |
| Модульный | Переходы задач по ролям, границы окна и ночного периода, зависимости и циклы, сохранение согласований при изменении окна или состава. Основной объём комбинаций проверяем здесь | Тестовый раннер бэкенда, табличные сценарии для бизнес-правил |
| Интеграционный | HTTP-контракт, права и ошибки, миграции, хранение статусов и истории, устаревшие ревизии и гонки. В частности, две команды на одну ревизию, откат при сбое записи и два внедрения с общей задачей | NestJS TestingModule, Supertest и отдельная PostgreSQL с миграциями |
| Компонентный UI | Предупреждение о неготовой задаче, добавление зависимости, меню перемещения, предпросмотр повторных согласований и сообщения сервера | Vitest и React Testing Library, ответы API задаём в тесте |
| Сквозной UI | Критические действия пользователя через браузер и сохранение результата после перезагрузки | Playwright, запущенные фронтенд, NestJS и отдельная PostgreSQL |

[Тестирование NestJS](https://docs.nestjs.com/fundamentals/testing) · [Профили запуска Playwright](https://playwright.dev/docs/test-projects)

## Сквозные сценарии

| Сценарий | Что проверяем в браузере |
| --- | --- |
| Доска и готовность | Инженер назначает задачу и перетаскивает её на проверку. Статус сохраняется после перезагрузки. Тестировщик видит очередь, берёт задачу, подтверждает проверку и видит события в истории. До подтверждения автор получает предупреждение при подборе и не может отправить заявку |
| Планирование | Инженер создаёт эпик и историю, запускает спринт, проверяет предупреждение о релизе и сохраняет итог переноса. |
| Перенос релиза | Автор применяет предложенное окно. В предпросмотре видны сохранённое решение владельца и повторная задача эксплуатации. После сохранения задача появляется в «На согласовании» у эксплуатации |
| Фактическое внедрение | Автор фиксирует внедрение подготовленного согласованного релиза. На доске видны номер и фактическое время, отметка сохраняется после обновления страницы |
| Учётные записи | Пользователь регистрируется. Администратор меняет его роль. Старый сеанс завершается, новый вход даёт роль тестировщика |
| Узкий экран | Пользователь открывает доску, меняет статус через «Переместить» и видит результат. В форме релиза предупреждение и нужное действие доступны на мобильной ширине |

Данные сценариев изолируем в тестовой БД. Для времени и календаря используем управляемые данные, а роли открываем в отдельных браузерных контекстах. Playwright ждёт наблюдаемых изменений интерфейса. При сбое сохраняем trace. Для мобильного прогона используем профиль Chromium с эмуляцией устройства.

Модульные, компонентные, интеграционные и браузерные проверки запускаются отдельными командами. В CI сначала идут форматирование, линтинг, типы и быстрые тесты, затем интеграции, сборка и браузерные сценарии. Отчёты покрытия бэкенда и фронтенда формируем в LCOV для SonarQube. При E2E_COVERAGE=true Playwright дополнительно сохраняет покрытие Chromium в frontend/coverage/e2e/lcov.info. SonarQube учитывает его вместе с отчётами Vitest и бэкенда. Результаты сценариев Playwright доступны отдельно.

## Доступность и понятность интерфейса

Playwright и axe проверяют контраст, подписи полей и доступные имена на экране входа, доске, в форме задачи и на мобильной карточке релиза. Клавиатурный сценарий проверяет открытие формы через Enter, закрытие через Escape и возврат фокуса на исходную кнопку. [Проверки доступности в Playwright](https://playwright.dev/docs/accessibility-testing)

Понятность проверяем отдельно с участниками, которые впервые видят «Окно». Дайте каждому сценарий без инструкции по кнопкам. Запишите первое действие, места остановок, подсказки и результат. После завершения попросите объяснить увиденное своими словами.

| Что попросить | Как понять, что участник разобрался |
| --- | --- |
| Передать задачу на проверку | Нашёл кнопку передачи, увидел очередь и может объяснить, как тестировщик возьмёт задачу и кому она вернётся при доработке |
| Собрать релиз с задачей, которая ещё проверяется | Нашёл причину в форме, сохранил черновик и объяснил условие отправки |
| Перенести окно и понять, кого это затронет | Нашёл предложение и правильно назвал согласование, которое сохраняется, и того, кто получит новую задачу |
| Найти фактическое время внедрения | Нашёл релиз из задачи и отличил согласованное окно от фактического времени |
