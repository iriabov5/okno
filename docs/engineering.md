# Правила разработки

## NestJS и TypeScript

- Используем feature-модули NestJS, конструкторный DI и явные границы ответственности. Контроллер принимает HTTP-запрос, DTO описывает контракт, сервис выполняет операцию, слой доступа работает с PostgreSQL.
- SOLID применяем там, где меняются обязанности или есть настоящая граница зависимости. KISS — один сервер, один механизм переходов, обычные функции для вычислений. DRY — общие правила маршрута и повторных согласований вызываются из предпросмотра и записи.
- Включаем strict. Входные данные из внешних источников валидируем на границе, неизвестные значения сужаем из unknown, состояния и результаты выражаем явными типами. Для разных исходов операции используем различимые варианты. Обрабатываем ошибки промисов и передаём транзакционный менеджер при связанных записях.
- Имена файлов и идентификаторы пишем по-английски. Документация, TSDoc, Swagger и пользовательские сообщения — по-русски. TSDoc описывает намерение, ограничения и побочные эффекты важных публичных контрактов и нетривиальных правил.
- Используем миграции TypeORM и отдельный seed для демо. Конфигурация и секреты поступают через окружение. Демо-пользователи и календарь включаются только в локальном демо-профиле.

## Swagger и OpenAPI

Используем @nestjs/swagger. Делаем короткий русский summary и содержательное описание операции, указываем поля, обязательность, форматы, примеры, доступ и возможные ответы. Операции, поля DTO, схему авторизации и ответы описываем декораторами Swagger. При изменении API сверяем сгенерированный контракт с ответами работающего сервера.

Запланированные адреса локального приложения — /docs для Swagger UI, /api.json и /api.yaml для контрактов. Схемы формируются из контроллеров и DTO на том же коде, который обслуживает запросы. Экспорт YAML получается из запущенного приложения. [Документация NestJS Swagger](https://docs.nestjs.com/openapi/introduction) · [Swagger CLI plugin](https://docs.nestjs.com/openapi/cli-plugin)

## Проверки и SonarQube

Запускаем форматирование, линтинг, проверку типов, сборку и проверки по [плану тестирования](testing.md). Модульные, интеграционные и UI-тесты добавляем вместе с соответствующими сценариями. Тесты бэкенда и фронтенда формируют LCOV, SonarScanner получает путь через sonar.javascript.lcov.reportPaths. Артефакты сборки и зависимости исключаются из анализа. Код приложения и миграции учитываются по назначению, тесты отмечаются как тестовый код.

В первом анализе проверяем, что анализатор распознал TypeScript проекта, импортировал LCOV и выдал Quality Gate. Версию локального анализатора и его Node.js сверяем отдельно от Node.js приложения. Конфигурацию сканера фиксируем при появлении исходников, адрес сервера и токен передаём через окружение. [Импорт покрытия JS/TS](https://docs.sonarsource.com/sonarqube-server/2026.1/analyzing-source-code/test-coverage/test-coverage-parameters)
