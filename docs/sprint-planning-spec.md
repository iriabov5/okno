# Планирование спринтов в «Окне»

Дельта-спецификация к исходной доске задач и заявкам на релиз. Порядок работы описан в [демонстрационном сценарии](demo.md#спринт-и-релиз).

## 1. Цель

Команда должна видеть цель ближайшего спринта, работу для её достижения и результат на момент завершения. Перед переносом незавершённой работы команда должна видеть, какие окна выкладки затронуты и почему.

Новизна для «Окна» — **предпросмотр переноса с учётом релизов**. В одном диалоге видно, какие карточки уйдут в следующий спринт, какие уже связаны с релизом и когда назначена выкладка. Например, если релиз запланирован на 20 ноября, а следующий спринт начинается 23 ноября, интерфейс показывает обе даты и номер задачи. Команда может изменить решение о переносе или отдельно пересмотреть план релиза. Предупреждения строятся по записанным датам и зависимостям.

## 2. Текущее поведение

- Доска получает карточки через `GET /api/v1/work-items`. В карточке есть система, разработчик, тестировщик, статус, обязательный предшественник и сведения о релизах. Доска показывает переходы от «К работе» до «Готова к релизу». Локальная доработка доски добавляет фильтр «Мои задачи» по разработчику и тестировщику. [Правила переходов](../backend/src/tracker/rules.ts)
- В `work_items` есть связь с системой и отдельная связь с обязательным предшественником. Тип карточки, принадлежность к эпику и планирование по спринтам отсутствуют. [Исходная схема](../backend/src/database/migrations/1760000000000-initial-schema.ts)
- Состав релиза задаётся через `release_request_items`. Действующие проверки определяют готовность задачи и её зависимостей к выпуску. История задачи уже содержит переходы и события релизов. [Проверки состава](../backend/src/releases/scope.ts) · [История задачи](../backend/src/tracker/tracker.ts)

## 3. Требуемое поведение

Подтверждённый запрос охватывает бэклог, эпики и пользовательские истории, запуск спринтов и перенос задач. Правила реализации и UX ниже описывают первую версию.

| ID | Условие | Требуемый результат |
|---|---|---|
| FR-01 | Команда открывает «Планирование» | Видит бэклог, активный и будущие спринты, а также список завершённых спринтов. Бэклог можно отфильтровать по системе, типу и эпику. |
| FR-02 | Пользователь создаёт или редактирует карточку | Может выбрать «Задача», «История» или «Баг», указать приоритет и связать карточку с эпиком её системы. Эпик показывает цель и связанные карточки. Список открывается фильтром по эпику в планировании. |
| FR-03 | Пользователь планирует спринт | Задаёт название, цель и даты, переносит карточки из бэклога, запускает спринт явным действием. Доска предлагает активный спринт и позволяет переключиться на все задачи. |
| FR-04 | Пользователь меняет план отдельной карточки | Выбирает бэклог, активный или будущий спринт. Карточка сохраняет статус, разработчика, тестировщика и связи с релизами. История показывает источник, назначение, автора и время. |
| FR-05 | Пользователь выбирает «Завершить спринт» | Видит цель, готовые карточки и список незавершённых. Выбирает бэклог или будущий спринт как общее назначение для незавершённых карточек. |
| FR-06 | Пользователь смотрит предпросмотр завершения | Видит предупреждения о сроках по затронутым задачам и релизам. Может раскрыть конкретные причины и проверить их до подтверждения. |
| FR-07 | Пользователь подтверждает завершение | Спринт закрывается, незавершённые карточки переносятся, результат сохраняется на дату закрытия. Итоги доступны после любых последующих переходов карточек. |
| FR-08 | Пользователь смотрит доску, карточку или релиз | На доске тип карточки различим по короткой подписи, в карточке видны эпик и спринт, в составе релиза видна принадлежность карточки к спринту или бэклогу. |

### Интерфейс

- В основной навигации появляется **«Планирование»**. На широком экране слева отображается бэклог, справа — активный и будущие спринты. На узком экране секции идут одна под другой. В бэклоге доступно действие «Новая задача» с выбором типа. У каждого спринта видны цель, даты, число карточек и действия, доступные пользователю.
- Основное действие у карточки в планировании — **«Перенести»**. Оно открывает список назначений и доступно с клавиатуры. Перетаскивание между колонками доски меняет статус.
- Спринты используют нейтральные подписи «Запланирован», «Активен», «Завершён». Акцентный цвет выделяет текущее действие, а предупреждение содержит читаемую причину и конкретные даты. На карточке доски название, текущий ответственный и следующее действие сохраняют визуальный приоритет. Тип виден на карточке, эпик и спринт — в её деталях.
- При запуске доска показывает цель и период активного спринта. Фильтр **«Мои задачи»** применяется к текущей выборке и сочетается с системой и спринтом. При отсутствии активного спринта доска показывает все задачи.
- Диалог завершения показывает итог и назначение переноса. Детали риска сгруппированы по номеру релиза. Подтверждение и возврат к выбору находятся внизу диалога, фокус после закрытия возвращается на кнопку открытия. Статусы и предупреждения доступны текстом и читаются без различения цветов.

## 4. Бизнес-правила

| Правило | Предлагаемое поведение |
|---|---|
| Область планирования | Одна команда ведёт одну доску и один активный спринт. Спринт может включать работу по нескольким системам. Эпик относится к одной системе, карточка может состоять в одном эпике своей системы. |
| Типы работы | История описывает результат для пользователя и критерии приёмки в существующем поле описания. Задача описывает конкретную работу, баг — дефект. Каждый из этих типов проходит текущие колонки. Эпик объединяет карточки и показывает количество готовых из общего числа. |
| Бэклог | В секции находятся карточки без спринта, кроме внедрённых. Приоритеты «Высокий», «Обычный», «Низкий». Внутри приоритета сначала идут более ранние карточки, при совпадении даты порядок определяется ключом. «Все задачи» на доске включает карточки независимо от спринта. |
| Жизненный цикл | `PLANNED → ACTIVE → CLOSED`. Запуск доступен при наличии хотя бы одной карточки и отсутствии другого активного спринта. Цель, название и период задаются при создании. Даты указываются календарными днями, начало не позднее окончания. Запуск и закрытие фиксируют фактическое время отдельно. У закрытого спринта видны количество готовых и перенесённых карточек. |
| Роли | Авторизованные пользователи видят планирование. Создание эпиков и спринтов, перенос, запуск и завершение доступны ролям «Инженер» и «Администратор». Создание и редактирование обычной карточки остаются по действующим правилам трекера. |
| Перенос | Одна карточка состоит в одном текущем спринте либо находится в бэклоге. Назначения — бэклог, запланированный или активный спринт. Перенос из завершённого спринта выполняется отдельным действием «Запланировать снова», если задачу вернули в работу. Исторический итог сохраняется. Уже внедрённая задача исключена из переноса. |
| Завершённая работа | На момент закрытия `READY` («Готова к релизу») считается завершённой для спринта. Она остаётся в закрытом спринте. Прочие карточки переносятся в выбранное назначение. Пустой активный спринт можно завершить с нулевым итогом. |
| Выпуск | Релиз может включать готовые карточки из разных спринтов и бэклога. Состав заявки, окно выкладки и решения согласующих меняются через существующие операции релиза. В подбор включаются истории, задачи и баги по действующим правилам готовности и зависимостей. |

### Правила предупреждений о релизе

Для каждого незавершённого элемента при завершении проверяются текущие связи с заявками на релиз, а также один прямой предшественник у карточек состава релиза. Результаты ограничены релизами, которые текущий пользователь вправе видеть в карточке задачи. Для видимой связи без права чтения самой заявки выводятся только номер и окно, доступные по действующей модели. Черновик видит только его автор. Каждое предупреждение содержит номер задачи, номер релиза и причину.

| Код | Условие | Текст по смыслу |
|---|---|---|
| `MOVED_AFTER_RELEASE` | Незавершённая карточка входит в невнедрённый релиз с окном, выбран будущий спринт, его первый день позже московской даты начала окна | «Выкладка 20 ноября. Следующий спринт начинается 23 ноября». |
| `MOVED_TO_BACKLOG` | Незавершённая карточка входит в невнедрённый релиз и переносится в бэклог | «Задача остаётся в релизе, дата выполнения в спринте больше не задана». |
| `DEPENDENCY_MOVED` | Переносимая незавершённая карточка — обязательный прямой предшественник карточки из невнедрённого релиза | «Задача OKNO-151 в составе REL-24 зависит от переносимой OKNO-142». |

Одна запись на пару «задача — релиз» содержит все применимые причины. Предупреждение информирует при выборе, перенос остаётся доступным. Если в предпросмотре есть видимая ссылка на релиз, она открывает существующую карточку заявки.

## 5. Изменения БД

| Таблица | Дельта |
|---|---|
| `epics` | `id uuid` PK, `system_id uuid` FK, `title varchar(160)`, `goal varchar(500)`, `created_by uuid` FK на пользователя, `created_at timestamptz`. Система, название и цель обязательны. |
| `sprints` | `id uuid` PK, `name varchar(120)`, `goal varchar(500)`, `starts_on date`, `ends_on date`, `state text`, `revision integer` от 1, `created_by uuid` FK, `created_at timestamptz`, `started_at timestamptz` и `closed_at timestamptz` по состоянию. Уникальное ограничение на активный спринт, проверка периода и допустимых состояний. |
| `work_items` | `type text NOT NULL DEFAULT 'TASK'`, `priority text NOT NULL DEFAULT 'NORMAL'`, `epic_id uuid NULL` FK, `sprint_id uuid NULL` FK. Ограничения на тип и приоритет. Связь с эпиком проверяет совпадение системы. Индексы по `sprint_id` и `epic_id` для выборок и подсчёта состава. |
| `sprint_results` | PK `(sprint_id, work_item_id)`, оба поля FK. `status_at_close text` с ограничением на статусы задачи. `destination_sprint_id uuid NULL` FK хранит место переноса незавершённой карточки. Для незавершённой `NULL` означает бэклог, для `READY` карточка осталась в спринте. Результат фиксируется при закрытии. |
| `work_item_events` | Новый вид `SPRINT_CHANGED` и два nullable поля `from_sprint_id`, `to_sprint_id` с FK. `NULL` означает бэклог. Событие использует существующие поля автора и времени и записывается вместе с изменением карточки. |

Миграция присваивает существующим карточкам тип «Задача» и обычный приоритет. Карточки получают пустые ссылки на эпик и спринт. Существующие связи с релизами, исполнители, статусы и номера сохраняются. Демоданные для новой функциональности подготавливаются отдельно от миграции.

## 6. Изменения API

Все пути ниже относительно `/api/v1`. Доступ — по действующей сессии и ролям из раздела 4. Строки названий и целей очищаются от пробелов по краям и валидируются после очистки. Идентификаторы — UUID, даты — `YYYY-MM-DD`, время событий — ISO 8601. Ревизия — целое число от 1.

| Метод и путь | Запрос | Успешный ответ |
|---|---|---|
| `GET /epics` | Опционально `systemId` | `200 { items }`. У каждого эпика `id, systemId, title, goal, readyCount, itemCount`. Порядок по названию и ID. |
| `POST /epics` | `systemId`, `title` 1–160, `goal` 1–500 | `201`, карточка эпика с нулевыми счётчиками. |
| `GET /sprints` | Без параметров | `200 { items }`. У каждого спринта `id, name, goal, startsOn, endsOn, state, revision, startedAt, closedAt, itemCount, readyCount`. Активный первым, запланированные по началу, завершённые по времени закрытия от новых к старым. Счётчики завершённых — из зафиксированного результата. |
| `POST /sprints` | `name` 1–120, `goal` 1–500, `startsOn`, `endsOn` | `201`, спринт в `PLANNED`. |
| `POST /sprints/{id}/start` | `expectedRevision` | `200`, активный спринт с фактическим временем запуска и новой ревизией. |
| `POST /sprints/{id}/completion-preview` | `expectedRevision`, обязательный `destinationSprintId` UUID или `null` | `200 { readyItems, movingItems, warnings, previewToken }`. Элементы списка содержат `id, key, title, status`, порядок по ключу. У предупреждения `itemKey, releaseKey, releaseId` (UUID или `null`), `releaseStartsAt` (время или `null`), `reasons` (коды из раздела 4), `dependentKeys` (номера зависимых карточек). Непрозрачный `previewToken` связывает подтверждение с показанным результатом. |
| `POST /sprints/{id}/complete` | Те же поля и обязательный `previewToken` | `200`, закрытый спринт с новой ревизией, фактическим временем закрытия и итоговыми счётчиками. |
| `GET /sprints/{id}/results` | Без параметров | `200 { items }` для закрытого спринта. Поля `id, key, title, statusAtClose, destinationSprintId`, порядок по ключу. Заголовок карточки берётся из её текущих данных, итоговый статус — из снимка. |
| `POST /work-items/{id}/sprint` | `expectedRevision`, обязательный `sprintId` UUID или `null` | `200`, карточка после переноса. Повторный выбор текущего назначения с актуальной ревизией возвращает карточку без нового события. |
| `GET /work-items` | Существующие параметры плюс опциональные `sprintId`, `epicId`, `type`, `backlog=true` | `200 { items }`. Фильтры сочетаются по И. При `backlog=true` возвращаются невнедрённые карточки без спринта. `sprintId` вместе с `backlog=true` даёт `400`. Без новых параметров сохраняется текущая выборка. |
| `POST /work-items`, `PATCH /work-items/{id}` | Существующие поля плюс опциональные `type`, `priority`, `epicId` | На создании значения по умолчанию `TASK`, `NORMAL` и `null`. На PATCH пропуск сохраняет текущее значение, `epicId: null` снимает связь. Для `type` и `priority` допустимы только значения перечисления. Правила редактирования деталей карточки распространяются на эти поля. |
| `GET /work-items/{id}` | Существующие параметры | Дополняет карточку и историю. Для `SPRINT_CHANGED` возвращает ссылки `fromSprint` и `toSprint` с `id, name` либо `null`. |
| `GET /release-requests/{id}` | Существующие параметры | Элементы состава дополняются текущей ссылкой на спринт либо `null`. |

Ответы с карточками добавляют `type` (`TASK`, `STORY`, `BUG`), `priority` (`HIGH`, `NORMAL`, `LOW`), `epic` (`{ id, title }` или `null`), `sprint` (`{ id, name, state }` или `null`). Пустые списки возвращаются как `[]`.

Ревизия спринта повышается при запуске, завершении и изменении его состава. Ревизия карточки повышается при смене спринта, в том числе в ходе завершения. При переносе между спринтами повышаются ревизии обоих спринтов, участвующих в операции. Состояние карточек, показанные предупреждения, назначение и пользователь входят в проверку `previewToken`.

Ошибки используют действующий формат `{ code, message, details? }`. Неверные параметры и эпик другой системы дают `400` (`INVALID_INPUT`, `EPIC_SYSTEM_MISMATCH`). Просроченная сессия даёт `401`, недостаток прав — `403`, отсутствующий ресурс по пути или неизвестное назначение — `404`. Устаревшая ревизия, недопустимое состояние, пустой спринт при запуске, второй активный спринт и устаревший предпросмотр дают `409` с кодами `STALE_REVISION`, `INVALID_STATE`, `SPRINT_EMPTY`, `ACTIVE_SPRINT_EXISTS`, `PREVIEW_CHANGED` соответственно.

## 7. Сценарии обработки

1. Инженер открывает «Планирование», создаёт эпик «Контроль доставки уведомлений» и спринт с целью «Оператор видит результат доставки». В бэклоге создаёт историю «Вижу статус доставки уведомления» и связывает её с эпиком. Из списка карточек переносит историю и техническую задачу в спринт.
2. Инженер запускает спринт. Доска показывает его состав. Разработчик ведёт карточку до проверки, тестировщик подтверждает готовность. Автор релиза может включить готовую карточку в заявку.
3. При завершении инженер выбирает следующий спринт для незавершённых задач. Предпросмотр показывает, что обязательный предшественник уходит в следующий спринт, а у зависимой карточки в релизе уже есть окно. Инженер проверяет предупреждение и подтверждает перенос. Завершённый спринт доступен в истории планирования.

| Сценарий | Условие | Ожидаемое поведение |
|---|---|---|
| Изменение плана перед подтверждением | После предпросмотра изменился состав, статусы, назначение переноса или связанные видимые релизы изменили показанные причины и даты | `409 PREVIEW_CHANGED` либо `STALE_REVISION`, никаких переносов. Интерфейс предлагает получить свежий предпросмотр. |
| Одновременный запуск | Два пользователя запускают разные спринты | Активным становится один. Второй получает `409 ACTIVE_SPRINT_EXISTS`. |
| Перенос и закрытие одновременно | Одна команда переносит карточку, вторая закрывает спринт | Результат соответствует порядку зафиксированных операций. Подтверждение со старым составом отклоняется. |
| Частичная ошибка | Операция завершения не смогла записать итог или перенос | Закрытие, снимок итогов, переносы и события выполняются одной транзакцией. При ошибке откатывается вся операция. |
| Повтор подтверждения | Первый запрос закрыл спринт, ответ потерялся | Повтор со старой ревизией даёт `409`. Интерфейс перечитывает состояние и открывает существующие итоги. Дубли событий отсутствуют. |
| Возврат после завершения | Готовую карточку вернули в работу после закрытия спринта | Итог закрытого спринта сохраняет `READY`. Текущая карточка доступна на общей доске и может быть запланирована снова. |

На подтверждении сервер проверяет актуальность предпросмотра в той же транзакции, где закрывает спринт. Проверка учитывает состав, статусы, назначение переноса и показанные предупреждения. Операции, меняющие эти данные параллельно, согласуются так, чтобы результат и предупреждения соответствовали одному состоянию данных.

## 8. Совместимость и границы задачи

Изменения HTTP-ответов добавочные. Статусы доски, правила работы тестировщика, существующие ссылки на релизы и согласования продолжают действовать для всех типов рабочих карточек. Страницы планирования используют существующую сессию. Границы первой версии определены в FR-01–FR-08. Подзадачи, оценки трудоёмкости, графики скорости, перетаскивание между спринтами и параллельные спринты относятся к последующим доработкам.

## 9. Критерии приёмки

| ID | Требование | Условия и действие | Проверяемый результат |
|---|---|---|---|
| AC-01 | FR-01, FR-02 | После миграции открыть планирование, создать историю и баг, связать историю с эпиком | Старые карточки видны как задачи. История находится по типу и эпику, баг виден отдельно. API отклоняет эпик другой системы. |
| AC-02 | FR-03, FR-08 | Запустить спринт с карточкой, открыть доску и применить «Мои задачи» | На доске видны цель и состав спринта. Фильтр скрывает чужие карточки. Через «Все задачи» виден остальной список. |
| AC-03 | FR-04 | Перенести карточку «На проверке» в будущий спринт | Сохранились статус, разработчик, тестировщик и состав релиза. В истории одно событие с автором и обоими спринтами. |
| AC-04 | FR-05, FR-06 | У незавершённой карточки есть релиз на 20 ноября, следующий спринт начинается 23 ноября | Предпросмотр показывает обе даты, номер карточки и релиза. При выборе бэклога видна причина отсутствия новой даты. |
| AC-05 | FR-06 | Переносимая задача — прямой предшественник карточки в видимом релизе, другая карточка есть в чужом черновике | Предупреждение указывает зависимость. Чужой черновик в ответ и интерфейс не попадает. |
| AC-06 | FR-05, FR-07 | Закрыть спринт с одной `READY` и одной `IN_TEST` | Первая осталась в итогах как готовая, вторая перешла в выбранное назначение. Последующая смена статуса не меняет сохранённый итог. |
| AC-07 | FR-03, FR-07 | Параллельно запустить два спринта или поменять статус перед подтверждением | Система оставляет один активный спринт. Устаревшее подтверждение не создаёт переносов и предлагает пересчитать итог. |
| AC-08 | FR-04, FR-07 | Тестировщик вызывает API переноса и завершения | Получает `403`. Данные и история не изменились. |
| AC-09 | FR-01, FR-05, FR-08 | На узком экране и с клавиатуры открыть планирование и завершить спринт | Секции читаемы, действие «Перенести» доступно без мыши, в диалоге можно выбрать назначение, прочитать предупреждения и подтвердить действие. |

## 10. Решения первой версии

| ID | Решение | Основание и влияние | Статус |
|---|---|---|---|
| D-01 | Один активный спринт на общую доску, эпики внутри системы | Можно планировать работу по нескольким системам без новой модели команд. Если нужны независимые команды, потребуется отдельная область планирования. | Принято для первой версии |
| D-02 | Инженеры и администраторы управляют спринтами | Используются текущие роли. При необходимости делегирования полномочия можно выделить отдельно. | Принято для первой версии |
| D-03 | `READY` закрывает работу для целей спринта | Совпадает с правой колонкой доски. Фактическое внедрение остаётся отдельным событием релиза. | Принято для первой версии |
| D-04 | Приоритеты в три уровня и перенос всех незавершённых в одно выбранное назначение при закрытии | Основной сценарий укладывается в один диалог. Индивидуальные назначения задаются через карточки до или после закрытия. | Принято для первой версии |
